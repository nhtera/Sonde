# Release runbook

Releases are cut from CI only, never from a developer machine: pushing a tag
is the only way to publish. This page is for whoever holds the maintainer
role: prerequisites to set up once, cutting a release candidate, cutting a
final release, verifying what got published, and recovering from a partial
or bad release.

## Prerequisites (one-time, before the first `v1.0.0-rc.1`)

- **Repositories** `nhtera/homebrew-tap` (casks under `Casks/`) and
  `nhtera/scoop-bucket` (manifests at the root). Both are shared with other
  nhtera tools, and GoReleaser only ever writes `Casks/sonde.rb` and
  `sonde.json`. There are no staging copies: a rehearsal publishes to them too.
- **`release` environment** on `nhtera/sonde` (Settings → Environments):
  required reviewers, and a deployment branch/tag rule restricting it to tag
  pushes. Both `.github/workflows/release.yml` and
  `.github/workflows/release-vscode.yml` run their publish job under
  `environment: release`, so nothing in this list can run without that
  approval gate.
- **`TAP_GITHUB_TOKEN` secret**, in the `release` environment only: a
  fine-grained PAT or GitHub App installation token with `contents: write`
  on exactly those 2 repositories, nothing else. GoReleaser uses it for both
  `homebrew_casks` and `scoops` (`.goreleaser.yaml`); the workflow's own
  `GITHUB_TOKEN` cannot push to a different repository, which is why this
  separate credential exists at all.
- **`VSCE_PAT` secret**, in the same `release` environment: a VS Code
  Marketplace personal access token for the `nhtera` publisher, used only by
  `release-vscode.yml`.
- **Marketplace publisher** `nhtera` created at
  [marketplace.visualstudio.com/manage](https://marketplace.visualstudio.com/manage).
- **Trademark check** confirmed (see [TRADEMARKS.md](../TRADEMARKS.md)) —
  gates tagging `v1.0.0` itself, not the rehearsal.

Nothing else is manual: SBOM (`syft`), checksums, and keyless signing
(`cosign` via GitHub OIDC — no key to generate or store) are all wired into
`.goreleaser.yaml` and `release.yml`.

## Cutting a release candidate (rehearsal)

A pre-release tag — anything with a semver prerelease part, e.g.
`v1.0.0-rc.1` — is marked a GitHub prerelease (`release.prerelease: auto`)
and publishes to the same tap and bucket as a final release, so
`brew install nhtera/tap/sonde` installs the candidate until the next tag
replaces it. Run every rehearsal exactly like a real
release:

```sh
git tag v1.0.0-rc.1
git push origin v1.0.0-rc.1
```

This triggers `release.yml` (`on.push.tags: ["v[0-9]*"]`): builds, archives,
`checksums.txt`, SBOM, cosign signature, then publishes the cask to
`nhtera/homebrew-tap` and the manifest to `nhtera/scoop-bucket`. It then
runs `verify-install` on a macOS/Linux/Windows matrix (`scripts/verify-install.sh "$VERSION"`, the tag
name passed through `env:` rather than interpolated into the shell command).

Rehearse `v1.0.0-rc.1` (or another `-rc.N`) all the way through, including
`verify-install`, before tagging `v1.0.0` itself — this is the point where
missing repos, a misscoped token or a Marketplace publisher problem should
surface, not on the real tag.

### API check before every tag

`make apicheck` (also a CI job) compares the public Go API with the ref in
`.api-baseline` and fails on an incompatible change. It is a no-op until
`v1.0.0-rc.1` exists. Before tagging, also run
`go run golang.org/x/exp/cmd/gorelease@v0.0.0-20260908205506-85c1c2202aba -base=<last tag> -version=<new tag>`:
it checks the whole module, including `go.mod`, and suggests the version.

## Cutting a final release

Once a rehearsal has gone green (signed artifacts, SBOM and checksums
published; `verify-install` green on all three OSes):

```sh
git tag v1.0.0
git push origin v1.0.0
```

Same workflow, same steps — the only difference is the tag has no
prerelease part, so `release.prerelease: auto` does not mark the GitHub
release a prerelease. A conventional-commits
changelog is generated by GoReleaser (`changelog:` in `.goreleaser.yaml`) —
this is the single changelog source; nothing is hand-maintained separately.

Every `1.y.z` after that follows the same two commands, straight to
production (no rehearsal tag needed once the pipeline itself is trusted,
though a `-rc.N` is still reasonable before a release with a large
compatibility or API change).

## Verifying signatures

Every release publishes `checksums.txt`, `checksums.txt.sigstore.json` (the
cosign bundle), and an SBOM per archive. Verify a release yourself:

```sh
cosign verify-blob \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/nhtera/sonde/\.github/workflows/release\.yml@refs/tags/v[0-9].*$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  checksums.txt
```

The regexp is anchored (`^`/`$`) with its literal dots escaped: unanchored,
or with unescaped dots (which match any character), it would also accept
certificates this release never produced.

Then check the archive you downloaded against the (now verified)
`checksums.txt` with `sha256sum -c` (or `shasum -a 256 -c` on macOS).
`scripts/verify-install.sh` runs this same check as part of its archive
step, and `verify-install.sh` also drives the brew/scoop/`go install` paths.

## Resuming a partially published GoReleaser run

If `release.yml`'s GoReleaser step fails partway (e.g. after archives and
checksums were created but before the tap/bucket push, or after one of the
two), do not retag. GoReleaser refuses to overwrite a GitHub release that
already exists for the tag by default, so:

1. Diagnose from the Actions log what completed (a partial GitHub release
   may already exist with some assets attached).
2. If the underlying problem is fixable without changing what would be
   built (e.g. `TAP_GITHUB_TOKEN` was missing or mis-scoped, a repo did not
   exist yet), fix that, delete the incomplete GitHub release (not the git
   tag), and re-run the workflow for the same tag from the Actions UI
   ("Re-run failed jobs" or "Re-run all jobs").
3. If the build itself needs to change, do not force-push or re-tag the
   same version — see "Roll-forward policy" below.

## Roll-forward policy

**Never delete or retag a published version.** Once a tag's release has
published (even partially, to any of the 4 external repos), treat that
version number as burned:

- A bad release is fixed by publishing a new patch version
  (`v1.0.1`, ...), not by force-pushing the same tag or deleting and
  recreating the GitHub release. Taps, buckets and `go install`'s module
  proxy cache may already have served the bad version to someone.
- For a genuinely broken version that must not be installed going forward,
  add a [`retract` directive](https://go.dev/ref/mod#go-mod-file-retract) to
  `go.mod`:

  ```
  retract v1.0.1 // panics on empty --data file; use v1.0.2
  ```

  This only affects `go install`/`go get` (it makes `go` tooling warn and
  refuse to select the retracted version by default); it does not touch
  already-published Homebrew/Scoop artifacts, which is why the affected
  version should also be pulled from the tap/bucket manifests in the same
  patch that adds the retraction, pointing users at the fixed version.

## VS Code extension release

Separate tag namespace, separate workflow, so the extension is never coupled
to a CLI release:

```sh
cd editors/vscode
npm version 1.0.0 --no-git-tag-version   # updates package.json only; commit it first
git tag editors/vscode/v1.0.0
git push origin editors/vscode/v1.0.0
```

`--no-git-tag-version` matters: plain `npm version 1.0.0` would also create a
local `v1.0.0` tag (npm's own convention), and pushing that would trigger
`release.yml` — the CLI's tag pattern (`v[0-9]*`) — for a version that was
never meant to cut a CLI release.

`release-vscode.yml` (`on.push.tags: ["editors/vscode/v*"]`) is two jobs:
`build-test` (no `environment:`, no secrets) checks `package.json`'s
`version` matches the tag (fails fast on a mismatch), builds `sonde` and
puts it on `PATH` (the extension's own test suite needs it), runs
lint/audit/tests, packages the `.vsix` with `vsce`, and uploads it as a
workflow artifact; `publish` (`environment: release`, `VSCE_PAT`) downloads
that artifact, publishes it to the Marketplace under publisher `nhtera`, and
attaches the `.vsix` to a GitHub release named after the tag — created with
`--latest=false`, so an extension release never becomes the repo's "Latest"
release (that should always be the most recent CLI tag). Splitting the jobs
this way means the job holding `VSCE_PAT` never runs `npm ci` or anything
else from the extension's own dependency tree — it only uploads a file
`build-test` already built and tested.
