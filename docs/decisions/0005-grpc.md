# 0005: gRPC

Status: Accepted. Date: 2026-09-28.

## Context

Phase 13 adds gRPC calls to Sonde: unary and server-streaming methods, with
message descriptors from `.proto` files, binary descriptor sets or server
reflection. Messages are written and checked as JSON, so the existing
queries, filters and predicates apply.

[0004](0004-streaming-protocols.md) set the frame this record reuses: Sonde
constructs exist only in `.sonde` files, under a `sonde` prefix, and a
`.hurl` file stays strict Hurl 8. It also planned to adopt Hurl's own gRPC
syntax in `.hurl` if Hurl had shipped it by now.

### Upstream Hurl (checked 2026-09-28)

|---|---|---|

Its draft file syntax is `POST http://host/pkg.Service/Method`, a ` ```grpc ` body fence and `grpc "status"` / `grpc "message"` queries, "to be refined". The Sonde design below follows the prototype's model where it has one: a
gRPC call is an HTTP/2 `POST` to `/package.Service/Method`, its status is
read from the response headers and trailers, and the `HTTP` line checks
the real HTTP status. A file written for Sonde therefore maps onto Hurl's
eventual syntax without a change of meaning.

## Decision

### Constructs

Two constructs, both valid only in `.sonde` files:

| Construct | Kind | Meaning |
|---|---|---|
| `[SondeGrpc]` | request section | Makes the entry a gRPC call and names where its message types come from |
| `sondeGrpc` | query | The call's gRPC status |

Server-streaming methods reuse 0004's `sonde-stream-*` options and the
`sondeStream` query. In a `.hurl` file, each construct is a parse error:
``section `[SondeGrpc]` requires a .sonde file`` and ``query `sondeGrpc`
requires a .sonde file``.

### The entry

```
POST http://localhost:50051/helloworld.Greeter/SayHello
x-request-id: {{id}}
[SondeGrpc]
proto: protos/helloworld.proto
{"name": "sonde"}
HTTP 200
[Asserts]
sondeGrpc "status" == "OK"
jsonpath "$.message" == "Hello sonde"
```

- **URL.** The path is `/package.Service/Method`. `https://` uses TLS
  and negotiates HTTP/2 with ALPN. `http://` uses cleartext HTTP/2 with
  prior knowledge (h2c), which is what gRPC servers expect. No other
  scheme is accepted: `grpc://` is not a URL scheme gRPC defines.
- **Method.** `POST` only; anything else is a runtime error.
- **Headers** are request metadata. `content-type`, `te` and names
  starting with `grpc-` are set by Sonde; setting one is a runtime error,
  except `grpc-timeout`, which replaces the deadline sent (see below).
  A binary metadata value (a name ending in `-bin`) is written base64, as
  on the wire.
- **Body.** The request message, as JSON: a JSON body, or a string,
  multiline string or `file,…;` body that holds JSON. Templates render as
  in any body. Without a body, the request is the empty message. `[Form]`
  and `[Multipart]` are runtime errors.
- **Options.** TLS (`cacert`, `cert`, `key`, `insecure`,
  `pinnedpubkey`), `connect-to`, `resolve`, `unix-socket`, IP family,
  `connect-timeout`, `max-time`, `delay`, `retry`, `repeat`, `skip`,
  `variable`, `verbose` and `output` apply as for HTTP. `http1.0`,
  `http1.1` and `http3` are runtime errors; `location` and redirects are
  ignored. An `http://` gRPC call through an HTTP proxy is a runtime error
  (h2c cannot cross it); `https://` through an HTTP proxy and SOCKS
  proxies work.

### `[SondeGrpc]`

The section holds `key: value` lines, like `[Query]`. Values are templates.

| Key | Repeatable | Meaning |
|---|---|---|
| `proto` | yes | A `.proto` source file, compiled at run time. |
| `import-path` | yes | A directory where `import` statements are resolved. Default: the directory of each `proto` file. |
| `protoset` | yes | A binary `FileDescriptorSet`, as written by `protoc --descriptor_set_out --include_imports` or `buf build -o`. |

Paths are relative to the request file and confined by the file root, like
every other file a request reads. Google's well-known types
(`google/protobuf/*.proto`) are always available.

With no `proto` and no `protoset` line, the section may be empty: Sonde
asks the server with **server reflection**, `grpc.reflection.v1` first and
`grpc.reflection.v1alpha` if the server does not implement v1. An error
names both tried. Reflection goes through the same connection settings as
the call.

Descriptors are loaded once per run for each distinct set of files, and
once per run unit and server for reflection.

Any other key is a parse error with a "did you mean" suggestion.

### Calls and results

- **Transport.** Sonde frames gRPC itself on its HTTP/2 client (5-byte
  length-prefixed messages, `te: trailers`, `grpc-timeout` from
  `max-time`, default 300 s). It does not use grpc-go. The call is an HTTP exchange like
  any other, so verbose output, timings, the `ip` query, certificates,
  redaction and events all work unchanged.
- **Compression.** Requests are sent uncompressed. Responses may be
  gzip-compressed (`grpc-encoding: gzip`); another encoding is an error.
  A received message is limited to 4 MiB, as in gRPC implementations.
- **Response.** The `HTTP` line checks the real HTTP status, which is
  `200` for any call a gRPC server answered. `grpc-status`,
  `grpc-message` and the other trailers are added to the response
  headers, so `header "grpc-status"` works too. The `body` query and
  `jsonpath` see the reply as JSON.
- **JSON mapping.** Messages use the canonical proto3 JSON mapping:
  lowerCamelCase field names, 64-bit integers as strings, enums by name.
  Fields holding their default value (`0`, `""`, `false`, an empty list)
  are **omitted**, as gRPC gateways and grpcurl do; assert them with
  `jsonpath "$.count" not exists` or write the proto3 default explicitly.
  A request may use the lowerCamelCase or the original field names;
  an unknown field is an error. `google.protobuf.Any` values are resolved
  from the loaded descriptors.
- **Unary methods** reply with one message: the response body. Zero
  messages with an OK status, or more than one, is an error.
- **Server-streaming methods** read the reply as a stream. With a
  `sonde-stream-*` option, the 0004 limits (`sonde-stream-count`,
  `-timeout`, `-max-bytes`) and stop reasons apply. Without one, the stream
  is read to its end like a body, bounded by `max-time` only: a stream
  stopped by the 10 s default would have no status, and would pass
  silently. Each message is an item of `sondeStream` (its JSON, as a
  string) and the body is a JSON array of the messages read. The status
  is known only if the server ended the stream; a stream stopped by a
  limit has none.
- **Client-streaming and bidirectional methods** are runtime errors.
- **A non-OK status fails the entry** with a runtime error at the URL,
  such as `gRPC status: NOT_FOUND: user 42 not found`, unless a capture or
  assert of the entry uses `sondeGrpc`. `HTTP 200` is true of every
  answered call, so without this rule a failing call would pass silently;
  an entry that expects an error says so with the query, as in example 3.
  When no `grpc-status` arrives, the status is derived as the gRPC
  specification says: from the HTTP status (for example 503 →
  `UNAVAILABLE`), from a content type that is not gRPC (`UNKNOWN`, for
  example a proxy's HTML page answering `200`) or from an HTTP/2 stream
  reset. The body of such a response is kept as received. A reset before the
  response headers leaves nothing to assert, so it fails the entry.
- **Deadlines.** `max-time` stays a hard limit, as in 0004: when it passes,
  the entry fails with a timeout error. Servers cancel a call at its
  `grpc-timeout` by resetting the stream, at nearly the same moment, so a
  test of a server's deadline sets a shorter `grpc-timeout` header itself.
  A server cancelling the call once its deadline has passed gives
  `DEADLINE_EXCEEDED` (as a gRPC client reports it), not `CANCELLED`.

### The `sondeGrpc` query

```
sondeGrpc              # the status name, as sondeGrpc "status"
sondeGrpc "FIELD"
```

| Field | Value |
|---|---|
| `status` (default) | The status name: `OK`, `NOT_FOUND`, `UNAVAILABLE`… |
| `code` | The status code, an integer: `0`, `5`, `14`… |
| `message` | The status message, percent-decoded; an empty string when none |

The field is checked at parse time, with "did you mean". On an entry that
is not a gRPC call, or a stream stopped before its status, the query
returns no value.

### Public API, events and reports

Additive under [stability.md](../stability.md), checked by `make apicheck`:

```go
const ProtocolGRPC Protocol = "grpc"   // Stream.Protocol of a server-streaming call

type GRPCStatus struct {
    Code    int    // 0 = OK
    Status  string // "OK", "NOT_FOUND", …
    Message string
}

// Response.GRPC is the status of a gRPC call; nil for any other entry,
// and for a stream stopped before the server sent its status.
GRPC *GRPCStatus
```

- Streamed replies send the existing `MessageReceived` events.
- The JSON report adds `sonde.grpc` (`code`, `status`, `message`) on the
  entry, and a server-streaming call has `sonde.stream` with protocol
  `grpc`. The HTML report shows the status next to the response.
- The request body shown in reports and verbose output is the JSON the
  file wrote, redacted as usual.
- `sonde export curl` skips a gRPC entry with a warning, and `--curl`
  leaves it out: curl cannot encode protobuf.

### Packaging

The plan's rule was: if gRPC adds more than 8 MB to the binary or 20 % to
the cold start, ship a `nogrpc` build tag and a `sonde-lite` artifact.
Without grpc-go, the new dependencies are `google.golang.org/protobuf`
(BSD-3-Clause) and `github.com/bufbuild/protocompile` (Apache-2.0), both
pure Go. Measured on darwin/arm64 with the release build flags
(`-trimpath -ldflags="-s -w"`, `CGO_ENABLED=0`), against the previous
commit:

| | Before | After | Change | Limit |
|---|---|---|---|---|
| Binary size | 17.3 MB | 20.9 MB | +3.6 MB | 8 MB |
| `sonde --version`, median of 300 interleaved runs | 7.64 ms | 9.02 ms | +18 % | 20 % |

Both are below the limits, so the rule is not triggered: one artifact ships,
with gRPC, and there is no `nogrpc` tag. About 0.7 ms of the start-up cost
is the package initialization of the protobuf runtime and the compiler; the
rest is the larger binary. The margin on start-up time is small: a later
dependency that adds to it should be measured against this table.
grpc-go itself, measured before this decision, would have added about
6.4 MB more.

## Examples

**1. Reflection, unary**

```
POST http://localhost:50051/helloworld.Greeter/SayHello
[SondeGrpc]
{"name": "sonde"}
HTTP 200
[Asserts]
sondeGrpc == "OK"
jsonpath "$.message" == "Hello sonde"
```

**2. A descriptor set over TLS, with metadata and a capture**

```
POST https://{{host}}/shop.v1.Orders/CreateOrder
authorization: Bearer {{token}}
[SondeGrpc]
protoset: build/shop.protoset
{"sku": "A-1", "quantity": 2}
HTTP 200
[Captures]
order_id: jsonpath "$.id"
[Asserts]
header "grpc-status" == "0"
```

**3. An expected error**

```
POST http://localhost:50051/shop.v1.Orders/GetOrder
[SondeGrpc]
proto: protos/shop/v1/orders.proto
import-path: protos
{"id": "missing"}
HTTP 200
[Asserts]
sondeGrpc "status" == "NOT_FOUND"
sondeGrpc "message" contains "missing"
```

**4. Server streaming**

```
POST http://localhost:50051/routeguide.RouteGuide/ListFeatures
[Options]
sonde-stream-count: 3
[SondeGrpc]
proto: protos/route_guide.proto
{"lo": {"latitude": 400000000, "longitude": -750000000},
 "hi": {"latitude": 420000000, "longitude": -730000000}}
HTTP 200
[Asserts]
sondeStream count == 3
sondeStream nth 0 jsonpath "$.name" isString
```

## Consequences

- `internal/grpcx` holds the framing, status mapping, descriptor sources and
  JSON mapping; `internal/httpx` gains an HTTP/2-only transport for gRPC
  calls and returns response trailers.
- The status names, the query fields, the auto-fail rule and the JSON
  mapping are part of the v1 contract once released.
- Tests run against an in-process server in the main module, and against
  grpc-go in a separate test module (`testdata/grpcinterop`,
  `make test-grpc-interop`) so that grpc-go never enters the release build.
- Out of scope: client-streaming and bidirectional calls, gRPC-Web,
  sending compressed requests, a `sonde-grpc-*` option family, command-line
  descriptor flags, and completion of service or method names in the
  editor.
- Revisit when Hurl ships gRPC. In `.hurl`, Sonde then adopts Hurl's
  syntax; the Sonde constructs keep working in `.sonde`.
